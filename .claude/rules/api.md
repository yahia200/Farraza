# API architecture

Loaded when you work in `apps/api` or `packages/shared`. The shared facts, docs table, commands, and the Prisma 8 basics are in the root `CLAUDE.md`. For NestJS, prefer the `.d.ts` files in `apps/api/node_modules/@nestjs/*`; for Prisma, `apps/api/prisma-8.md` and `prisma <command> --help`.

## Layering per feature module

Each feature folder (`companies`, `jobs`, `forms`, `applications`, `pipeline`, `users`, `auth`) follows the same layering:

- **Controller**: routing and param/DTO binding only.
- **Service**: business rules, authorization checks, and mapping outcomes to HTTP exceptions.
- **Repository**: the only layer that touches `PrismaService` (exception: the `@nestjs/authentication` stores in `auth/`, see below). It maps rows through local `toX()` functions into plain domain types and never returns raw ORM rows.
- **`<feature>.ts`** (such as `company.ts`, `job.ts`, `pipeline.ts`): the domain interfaces and constants. For example, `DEFAULT_STAGES` lives in `jobs/job.ts`, and the `STATUS_FOR_STAGE`/`EVENT_FOR_STAGE` maps live in `pipeline/pipeline.ts`.
- **DTOs**: request bodies are validated by **Zod schemas from `@repo/shared`**, not class-validator.
  - A DTO file (`dto/*.dto.ts`) re-exports its schema and declares the DTO as a type: `export type CreateJobDto = CreateJobInput`.
  - Controllers attach the schema with `@Body({ schema: createJobSchema }) dto: CreateJobDto`. Import the DTO with `type`, which `isolatedModules` plus `emitDecoratorMetadata` require.
  - The global `StandardSchemaValidationPipe` (`main.ts`) validates every parameter that declares a schema and passes the parsed output to the handler.
  - Use `z.strictObject` for bodies, so unknown keys are rejected.
  - Failures return 400 `{ message, errors: [{ path, message }] }` via `common/validation-errors.ts`, the same shape services use for form and answer errors.
  - Docs: https://docs.nestjs.com/application/validation

The package is `"type": "module"`, so relative imports must use the `.js` extension (`import { X } from './x.js'`).

## Auth, tenancy, and authorization

1. **Authentication** is global. Session cookies come from `@nestjs/authentication`; `SessionAuth` loads the user, and `PrismaSessionStore` persists sessions in the `sessions` table. Every route requires a session unless it is marked `@Public()`, as `AuthController` and the applicant-facing `PublicController` are. Get the user with `@CurrentUser()`.
2. **Tenancy**: company-scoped controllers are mounted at `companies/:companySlug/...` and use `@UseGuards(CompanyMemberGuard)`. The guard looks up the user's membership by slug, throws **404, not 403**, for non-members so that company existence isn't leaked, and sets `request.membership`. Read it with `@CurrentMembership()`. The resulting `Membership` (`{ userId, role, company }`) is the only path from a slug to a `companyId`.
3. **Authorization**: services call `await this.authorization.authorize(SomePolicy, 'action', user, membership, ...)`. Policies are `@Policy()` classes holding role checks (`CompanyPolicy`, `MemberPolicy` with role ranking, `JobPolicy`, `ApplicationPolicy`) and must be listed in their module's `providers`. Roles: `owner > admin > recruiter = interviewer`. Interviewers can read, add notes and rate, but can't edit jobs or move candidates.
4. **Tenant isolation**: every company-owned table has a `companyId`. Repositories filter by it (along with `jobId`) on reads, and copy it from the parent on inserts.

### Email verification, password reset, Google sign-in (`auth/`)

The package (`@nestjs/authentication`) creates, mails and checks the links; the app plugs in through handlers that register themselves in their constructors. Guide: `docs/nestjs/auth.md` ("Verify email addresses", "Reset forgotten passwords", "Add "Sign in with Google"").

- **Email verification**: `EmailVerificationController` (`POST auth/email/verify`, public, token in the body; `POST auth/email/verification`, signed-in resend, 202, 409 once verified, 5 per 10 min) → `VerificationService` (wraps `EmailVerificationService`; `sendAfterSignUp` logs a mail failure instead of failing sign-up) → `EmailVerificationMailer` (the `emailVerification` handler: sends `VerifyEmailMail`, `markVerified` is the repository's conditional update on id + current email).
- **Password reset**: `PasswordResetController` (`POST auth/password/forgot`, 202 before the lookup, 5 per 10 min; `POST auth/password/reset`, signs in) → `PasswordRecoveryService` (wraps `PasswordResetService`; the package ends other sessions and marks the address verified) → `PasswordResetMailer` (the `passwordReset` handler: finds the account by its stored address, sends `PasswordResetMail`, stores the new hash). The password rules are `newPasswordSchema` in `@repo/shared`.
- **Mail**: `MailModule.forRootAsync` in `app.module.ts` (`@nestjs/mail`): `SmtpTransport` when `SMTP_URL` is set, else `LogMailTransport` (dev and tests; `env.schema.ts` refuses to boot in production without `SMTP_URL`). Bodies are `FileTemplateEngine` HTML templates in `src/mail/templates/`, which `nest-cli.json` `assets` copies to `dist/mail/templates/` (tsc doesn't copy HTML). Links point at the web app (`emailVerification.url`, `passwordReset.url` = `APP_URL` + `/verify-email`, `/reset-password`), whose pages POST the token back.
- **Stores**: `PrismaEmailTokenStore` (`email_tokens`, both purposes), `PrismaOidcStateStore` (`oidc_states`), `PrismaRefreshTokenStore` (`refresh_tokens`, `revoked_refresh_families`) and `PrismaMfaStore` (`mfa_totp`, `mfa_recovery_codes`, `mfa_failures`) register with `AuthenticationStorage` like `PrismaSessionStore`. The last two exist because the package's production guard needs a store for every contract a configured feature reads; the `accessToken` and `mfa` options are not configured yet, so nothing writes to them (`.scratch/auth-token-stores/spec.md`). All five query `PrismaService` directly: a documented exception to "only repositories touch Prisma", because their shape is the package's store contract, not a domain type. The email-token and OIDC-state stores consume with one atomic delete-and-return, and their saves prune expired rows and cap the table (`maxPending`). The refresh-token and MFA stores use conditional updates and deletes instead, and prune expired rows without a cap (rules: `docs/db-schema.md` §7).
- **Google** (ADR-0003): `AccountLinker` (the `oidc` resolver) maps a Google identity to a user by `(provider, subject)` in `identities`, links by email only when both Google and our account verified it, and otherwise refuses with 403 `errorCode: PASSWORD_SIGN_IN_REQUIRED` (`@repo/shared` `oidc.ts`, with the message the web shows). `OidcController` answers JSON `{ url, cookies }` instead of redirecting, so the web Route Handlers can set the cookies on the web origin; its login query (`link`, `redirectTo`) is validated by `oidcLoginQuerySchema` (`auth/dto/oidc-login.dto.ts`, API-only), and the callback query goes to the package unvalidated. `oidc.callbackUrl` is on the web origin (`oidc.options.ts`).
- **CSRF**: `app.enableCsrfProtection({ trustedOrigins: [APP_URL] })` in `main.ts` refuses cross-site writes to every route. Server Actions call server-to-server without `Origin`/`Sec-Fetch-Site`, so they pass; the OIDC routes are GETs, and the web login handler forwards `Sec-Fetch-Site` so a link flow started from another site is still refused.

A global `ThrottlerGuard` allows 100 requests/min. The public apply endpoint is tighter (5 per 10 min). Limits are per visitor: `apiFetch` sends the visitor's address in `x-client-ip` plus `x-internal-secret`, and `TrustedClientThrottlerGuard` (`common/trusted-client-throttler.guard.ts`) uses that address only when the secret matches; otherwise it counts the caller's own connection. There is no Express `trust proxy`: the web app runs on Vercel (no fixed address) and the API on Cloud Run. The address comes from `X-Forwarded-For`, which Vercel overwrites with the real client address; `next dev` fills it from the connection. Counts are in memory, which is correct only while the API runs as a single instance (Cloud Run max instances = 1); more instances would need shared storage.

## Background work (`recheck/`, ADR-0007)

`@nestjs/bullmq` + `bullmq` on its PostgreSQL backend, worker inside the API process, queue tables in BullMQ's own `bullmq` schema (not in the contract; `docs/db-schema.md`). `RecheckModule` calls `setDefaultBackendFactory(createPostgresBackend)` in the `BullModule.forRootAsync` factory, because `@nestjs/bullmq` has no per-queue backend option and builds queues with `new Queue(name, options)`; the connection is `{ connectionString: DATABASE_URL, migrate: true }` (without `migrate: true` BullMQ only checks the schema, never creates it). The options type only models Redis, hence the `as never`. `RECHECK_QUEUE` is the queue name; `RecheckProcessor` is the worker, a thin adapter to `RecheckService.run` (see "Re-check" below). A job interrupted by a restart is picked up again as stalled after about 30 s and **runs from the start**, so processors must be idempotent.

**Re-check (keyword match, ticket 07).** Routes under `companies/:companySlug/jobs/:jobSlug/recheck` (`RecheckController`, `CompanyMemberGuard`, so a foreign tenant's Job is 404): `GET` → `{ count }`; `POST` (202, `JobPolicy` `update` like the Requirements `PUT`, interviewers 403) → the status; `GET .../status` → `{ state: 'running', processed, total }` or `{ state: 'idle', lastRun: { finishedAt, processed, failed } | null }`. The two `GET`s need only membership (no policy), like the Job `GET`. `RecheckService` holds everything: `count` (zero without a version), `start`, `status` and `run`, the processor body; `RecheckProcessor` only forwards `job.data` and `job.updateProgress`. One run per Job: the BullMQ jobId is `recheck-<jobId>` (`recheckJobId`); `start` does nothing while that job is waiting/active, removes a finished one first (it is kept as the "last run" the status reads), and queues nothing when the count is zero. `run` loops: each chunk (`RECHECK_CHUNK_SIZE`, 50) re-reads the Job's current version, takes the next Applications still behind it (`RecheckRepository.findNeeding`, raw SQL because the contract has no Application back-relations to File/CvText), upserts their results and reports `{ processed, total: processed + remaining }`; because finished Applications leave the selection, an edit made mid-run is picked up by the next chunk and a restart-from-the-start (see above) only redoes what is missing. Job attempts: 3 with exponential backoff. Specs: `recheck.service.spec.ts` (fake repository and fake queue); the SQL and the Postgres backend are covered by a manual run against the dev database, not a spec.

**Observed in the ticket 09 run (real API, dev Postgres).** Saving, the submit-time result, the count (3), the run (progress `0 / 3`, then idle, count 0) and the newer-version re-run all behaved as written above. Things to know: (1) a CV under 100 characters is `unreadable`, so test CVs need a few lines; (2) the public submit is throttled at 5 per 10 minutes per visitor, so a manual pass of more than five Applications has to wait or restart the API (the counts are in memory); (3) killing the API mid-run and restarting it did not resume the run within about a minute (status went back to idle with the count unchanged), unlike the ADR's ~30 s stall pickup in the spike, so a manager simply clicks Re-check again; the processor is idempotent either way; (4) the web board reads through `use cache: private`, so the web app must revalidate the candidates path when a run ends (`refreshCandidates`, see `web.md`). Open, still the owner's: whether Cloud Run runs with CPU always allocated (ADR-0007), without which a run only advances while a request is being served.

## Embedding match scoring (`embedding-match/`, Layer 3 ticket 06)

`EmbeddingMatchService.score({ companyId, jobId, applicationId })` is the whole scoring flow for one Application; nothing queues it yet (ticket 07 adds the submit hook and queue), and `EmbeddingMatchModule` is not imported by `AppModule` until then. It answers a `ScoreOutcome`: `disabled` (`EMBEDDER` is null), `no_requirements` (no version or an empty current list: nothing written), `no_cv` (no uploaded CV file or no `cv_texts` row: nothing written), `not_scored` with a reason, or `scored`. Order: embedder, current Requirements, CV text; a CV whose `cv_texts.status` is not `readable` (`unreadable` or `failed`) is `not_scored / cv_unreadable` with no embedder call. Then it ensures the version's `requirement_embeddings` (missing ones embedded together as `query`, written insert-or-ignore, then **all read back** so a racing worker's rows are the ones used), embeds `chunkCvText(text)` in one `document` call, replaces the Application's `cv_chunk_embeddings`, and scores with `scoreApplication` from `@repo/shared`. An `EmbedderError`, a wrong vector count or a vector not `dimensions` long ends as `not_scored / embedder_failed` (any other error propagates, so a bug or a database failure is a failed job that retries, not a stored "not scored"); `model_mismatch` or `length_mismatch` from the scorer ends as `not_scored / model_changed` (the chunk vectors are kept). The service returns instead of throwing on `embedder_failed`, so the queue (ticket 07) decides whether to rethrow for a retry. The row is an upsert on `application_id` (`EmbeddingMatchRepository.saveScore`), so a retry or a second run leaves one row. Spec: `embedding-match.service.spec.ts` (in-memory fake repository, fake `Embedder`); the SQL, `real[]` round trip and insert-or-ignore are covered by a manual run against Postgres and Ollama.

## Concurrency and error conventions

- Writes are **conditional**, not read-then-write. Example: `move` updates `where({ id, stageId: from.id })`, job `open`/`close` filter on the current status, and a draft update filters on `publishedAt IS NULL`. When the repository gets back `null`, the service throws `ConflictException` with a "reload and try again" message. The deliberate exceptions are saving a Job's Highlighted questions, a Job's rating Criteria and a Job's Screening rules: one unconditional `UPDATE` replaces the whole list, because each is a preference and last-write-wins loses no data (comments on `JobsRepository.replaceHighlightedQuestionKeys`, `replaceRatingCriteria` and `replaceScreeningRules`). A third is a Member's own Rating (`PipelineRepository.saveRating`): an upsert of the caller's own row, last-write-wins, whose worst case is a slightly wrong `previous` in the event.
- Unique-constraint races are caught with `isUniqueViolation()` (`common/db-errors.ts`, SQLSTATE 23505) and turned into `ConflictException`, or into a `'duplicate'` result.
- Slugs come from `slugify()` (`common/slugify.ts`). On collision, a random 4-hex suffix is appended.

## Domain flow

1. **Company**: created together with an `owner` membership in one transaction. Members are added and removed under `MemberPolicy` rank rules.
2. **Job**: created in `draft` with six default stages (Applied, Screening, Interview, Offer, Hired, Rejected; see `DEFAULT_STAGES`). Stage `kind` is `normal`, `hired`, or `rejected`.
   - **Highlighted questions** (`jobs.highlighted_question_keys`, `docs/db-schema.md` §3.5): every Job payload (`GET .../jobs` and `GET .../jobs/:jobSlug`) carries `highlightedQuestionKeys: string[]`, the list as last saved, stale keys included. `PUT .../jobs/:jobSlug/highlighted-questions` with `{ keys }` (`saveHighlightedQuestionsSchema`: at most `HIGHLIGHT_LIMIT` UUIDs, no repeats) → `JobsService.saveHighlightedQuestions`: `JobPolicy` `update` (interviewers 403), the job lookup (another company's job 404), then `FormsRepository.findLatestPublished` (none: 409), then `checkHighlightKeys(keys, form.fields)` (400 `{ message, errors: [{ path: 'keys.<index>' }] }` for a key not on that form or not highlightable: the service prefixes the shared check's `<index>` with `keys.`, so every 400 on this route, the validation pipe's `keys`/`keys.<index>` included, is a path into the request body), then `JobsRepository.replaceHighlightedQuestionKeys`. It answers `{ keys }`. `FormsRepository` comes from `FormsRepositoryModule` (`forms/forms-repository.module.ts`), which `FormsModule`, `JobsModule` and `PipelineModule` import: `JobsModule` can't import `FormsModule` for it, because `FormsModule` already imports `JobsModule` (a circular module import), so the repository has a module of its own, as the Nest circular-dependency guide suggests (https://docs.nestjs.com/fundamentals/circular-dependency).
   - **Rating Criteria** (`jobs.rating_criteria`, `docs/db-schema.md` §3.5): every Job payload carries `ratingCriteria: string[]`, the catalog keys as last saved (`[]`: rated on the overall alone). `PUT .../jobs/:jobSlug/rating-criteria` with `{ keys }` (`saveRatingCriteriaSchema`: at most `RATING_CRITERIA_LIMIT` catalog keys, no repeats) → `JobsService.saveRatingCriteria`: `JobPolicy` `update` (interviewers 403), the job lookup (another company's job 404), then `JobsRepository.replaceRatingCriteria`. Any Job status, and no published form is needed, because the catalog is fixed. The service does no key check of its own: the body schema, applied by the validation pipe, is the whole validation, so a bad key, more than five or a repeat is a 400 with `keys`/`keys.<index>` paths before the service runs. It answers `{ keys }`. Changing it never touches Ratings already given.
   - **Screening rules** (`jobs.screening_rules`, `docs/db-schema.md` §3.5, ADR-0005): every Job payload carries `screeningRules: ScreeningRule[]` as last saved (`[]` for none). `PUT .../jobs/:jobSlug/screening-rules` with `{ rules }` (`saveScreeningRulesSchema`: an array of at most `SCREENING_RULES_LIMIT`, items not checked) → `JobsService.saveScreeningRules`: `JobPolicy` `update` (interviewers 403), the job lookup (another company's job 404), `FormsRepository.findLatestPublished`, then `parseScreeningRules(dto.rules, form?.fields ?? [])` (400 `{ message, errors: [{ path: 'rules.<index>.<path>' }] }`; the service prefixes the shared check's `<index>.<path>` with `rules.`; a Job with no published form passes `[]` as the fields, so only an empty list is accepted, and that is a 400, not Highlighted questions' 409, so clearing still works), then `JobsRepository.replaceScreeningRules`. Any Job status. It answers `{ rules }` (the parsed rules as stored).
   - **Requirements** (`job_requirement_versions`, `docs/db-schema.md` §3.23, `.scratch/keyword-match/spec.md`): `JobWithStages` (so the `GET .../jobs/:jobSlug` payload and `JobsService.get`) carries `requirements: Requirement[]` and `requirementsVersion: number` (the highest version's list and number; `[]` and `0` before the first save). `PUT .../jobs/:jobSlug/requirements` with `{ requirements }` (`saveRequirementsSchema`, whole list validated by the body schema: at most `REQUIREMENTS_LIMIT`, unique ids, each with 0 to 15 keywords: a keyword-less Requirement is valid and reads "not checked", Layer 3 ticket 04) → `JobsService.saveRequirements`: `JobPolicy` `update` (interviewers 403), the job lookup (404), then `isDeepStrictEqual` against the current list (identical: nothing written, answers the current version) else `JobsRepository.createRequirementVersion` with `version + 1` (one `INSERT`; UNIQUE (`job_id`, `version`) loses a race as `ConflictException` 409). Any Job status, **below the Edit limit** (layer 3 ticket 05): `saveRequirements` first counts the Job's Applications (`JobsRepository.countApplications`, every status, rejected included) and, at `REQUIREMENT_EDIT_LIMIT` (100, `@repo/shared`) or more, throws a 409 `ConflictException` ("...can no longer be changed") for any role and for an unchanged list too, writing nothing; the count is not in the insert's transaction, so a save racing the 100th submit can still land. `GET .../jobs/:jobSlug` goes through `JobsService.getDetail`, which adds `requirementsLocked: boolean` (`JobDetail`); `JobsService.get`, the lookup other services share, does not, so no other payload and no public one carries it. It answers `{ requirements, version }`. Versions are immutable and Requirement ids are the client's, kept when an existing one is edited. Never in a public payload.
3. **Form** (`form_versions`): at most one draft per job, enforced by a partial unique index. Published versions are **immutable**: editing after publish creates a new draft with `version + 1`, and applicants always get the latest published version. A job can't be opened until a published form exists. Each version also has `cv_mode` (off, optional, required; ADR-0002), saved with `fields` (`saveFormSchema` takes both) and part of the public job payload. **Publish is blocked by Screening rules** (ADR-0005, `FormsService.publish`): the Job's stored `screeningRules` are checked against the draft; a dropped question, a changed question type or a removed option a rule uses is a 400 `{ message, errors: [{ path: 'screeningRules.<i>.questionKey' | 'screeningRules.<i>.condition.optionIds.<j>', message }] }` (messages name the rule's question and option; same `BadRequestException` shape as `saveDraft`). Drafts save freely; no rules, no check.
4. **Public apply** (`GET/POST /api/public/:companySlug/:jobSlug[/applications]`, in `applications/`):
   - Only `open` jobs are served. Fields go through `toPublicFields()`, which still strips the retired field-level reject settings from versions saved before ADR-0005 (the API reads stored `fields` without parsing them); never send raw `fields` to applicants.
   - Answers are validated with `parseAnswers()`. `ApplicationsService.submit` then runs `evaluateScreeningRules(job.screeningRules, form.fields, answers, Temporal.Now.plainDateISO('UTC'))` (`OpenJob.screeningRules` is read by `findOpenJob`). Any fired rule with outcome `reject` auto-places the application in the Rejected stage (`status = 'rejected'`) and adds an `auto_rejected` event after `applied`, in the same transaction, with `data: { rules: FiredRule[] }` (only the reject ones, each `{ ruleId, questionKey, questionLabel, outcome, reason }`). Fired rules with outcome `flag` are stored on the Application (`applications.flags`: `[{ ruleId, questionKey, questionLabel, reason }]`, `[]` for none; `NewApplication.flags`) and written as a `flagged` event after `applied` (and after `auto_rejected` when a reject also fired) with `data: { rules: <the same list> }`; the Application is not moved by a flag. So `auto_rejected` carries the reject rules only and `flagged` the flag rules only, and when both fire the Application is rejected with both events and the flags stored. Rules, flags and reasons never appear in a public payload (spec'd in `applications.service.spec.ts`, "returns no rules or reasons from any public route"). Field config carries no rules (ADR-0005): `parseFormFields` strips the two retired reject properties from any stored version instead of failing, so old versions still load and take Applications.
   - **Requirement result** (keyword match ticket 04, `docs/db-schema.md` §3.24): `findOpenJob` also reads the Job's current Requirements version (`OpenJob.requirements: { version, list } | null`, the highest `job_requirement_versions` row, scoped by company and job; never in a public payload). `ApplicationsService.submit` builds `NewApplication.requirementResult` with `checkRequirements`: null unless the Job has a version and the CV text it just built is `readable`, else `{ version, results: matchRequirements(list, text), missedMustHave }`. `ApplicationsRepository.submit` writes it as the last insert of the same transaction (`ApplicationRequirementResult.create`, UNIQUE (`application_id`)), so a refused file rolls it back. An empty-list version still writes a row. The matcher is pure, so it cannot fail a submit.
   - A non-empty hidden `website` field is treated as a bot honeypot: the API returns success without saving anything.
   - Candidates are per-company (unique `companyId + email`, upserted). A job takes one application per candidate, per email and per phone: `applications` stores the submitted email and phone with UNIQUE (`job_id`, `email`) and (`job_id`, `phone`), so a repeat is rejected by the database (409).
   - **CV upload** (ADR-0002): `POST .../uploads` (`createUpload`, throttled 20 per 10 min per visitor, separate from submit's 5) checks the declared name, type and size against the open job's published form (CV: PDF or DOCX, up to 5 MB, `cv_mode` not `off`), inserts a pending `files` row and returns `{ fileId, url, contentType }`: a presigned PUT that signs the content type and length (`StorageService.createUpload`). The web app's Server Action calls it; the browser PUTs the bytes to the bucket. Submit takes an optional `cvFileId`: `required` without one is a 400 on `cvFileId`, `off` with one is a 400, and the file is attached inside the Application transaction with a conditional update (same job, purpose and field key, unattached, `pending`). A refused attach rolls back and answers 409 with `errors: [{ path: 'cvFileId' }]`; a duplicate Application or a validation error leaves the file pending, so a retry can reuse it. Objects are keyed by company, job and file id only (`docs/db-schema.md` §9). **Submit-time check** (`verifyFiles`, before the transaction, after answers and CV mode are validated): for each referenced pending file of this job, `StorageService.headObject` must find the object with exactly the declared `size_bytes`, and `readLeadingBytes` (first 64 KiB, `SNIFF_BYTES`) fed to `sniffFileType` (`storage/file-sniff.ts`, `file-type`'s `fileTypeFromBuffer`) must give an allowed type (CV: PDF or DOCX). A file that fails has its object deleted, then its row (conditional on pending and unattached), and the submit answers 400 `errors: [{ path: 'cvFileId' }]`; the sniffed type is passed on in `FileToAttach.mimeType` and stored by the attach. An id that is not a candidate at all (unknown, another job's, already attached) is the 409 above.
   - **Attachments** (file questions, ticket 07): `createUploadSchema` is a union on `purpose`: `'cv'`, or `'answer'` with the question's `fieldKey`. For an answer, `createUpload` finds the file question on the open job's published form (400 on `fieldKey` if it isn't one) and checks the declared type and size with `checkAttachmentFile(question.config, dto)` from `@repo/shared` (the browser runs the same function first); the pending row is `purpose = 'answer'` with that `field_key`. The question config is `{ kinds, maxSizeMb, maxDurationSeconds }`; `FILE_KIND_TYPES` in `packages/shared/src/files.ts` maps a kind to its content types (document: PDF, DOCX; image: JPEG, PNG, WebP; never SVG) and video is MP4, MOV, WebM and audio is MP3, M4A, WAV, OGG, WebM (ticket 09). `maxDurationSeconds` is required (whole seconds ≥ 1) when video or audio is allowed and null otherwise (`parseFormFields`). The create-upload body may carry `durationSeconds` (answer purpose only), which the browser read from the file; `checkAttachmentFile` requires it for a video/audio type and compares it with the limit, and `createUpload` stores it on the pending row (null for a document or image) — the server never re-measures it. The declared and the sniffed type both go through `matchAllowedType` (aliases like `audio/x-m4a`, parameters like `; codecs=opus`, and `video/mp4`/`video/webm` standing for the audio type where only audio is allowed, because file-type cannot tell an audio-only WebM/MP4 from a video); the allowed type it returns is what the presigned PUT pins and what is stored in `mime_type`. Submit takes the file id from `answers` (`parseAnswers` already checks it is a uuid and enforces `required`); `wantedFiles()` lists the CV and every file answer with the types its bytes may be, and `verifyFiles` + the attach then work as for the CV. A file only matches if its row has the same purpose and `field_key` as the slot it is submitted for, so another question's file, the CV, another job's or an attached file is a 409 whose `errors` path is the question key (the repository's `file_conflict` result names the file). A bytes mismatch is a 400 on the question key and the object is deleted.
   - Phones are normalised to E.164 by `phoneSchema` (`packages/shared/src/phone.ts`, libphonenumber-js, default country `EG`) and checked by a CHECK constraint; never store a phone without it.
5. **Pipeline** (`pipeline/`): kanban board, application detail, stage moves (the target stage's `kind` sets the application `status`), notes, and Ratings.
   - **Rate** (`.scratch/ratings/spec.md`, `docs/db-schema.md` §3.16): `PUT .../jobs/:jobSlug/applications/:applicationId/rating` with `{ overall, criteria? }` (`saveRatingSchema`, `dto/save-rating.dto.ts`) → `PipelineService.rate`: `ApplicationPolicy` `rate` (all four roles, like `addNote`), `jobs.get` (another company's job 404), `currentStageOf` (the private helper `move` shares: `findStageOf(companyId, jobId, applicationId)` plus the Stage in `job.stages`; another company's or job's Application 404; any status is fine), then `checkRatingCriteria(dto.criteria ?? {}, job.ratingCriteria)` (400 `{ message, errors: [{ path: 'criteria.<key>' }] }`, the service prefixing the shared check's key), then `PipelineRepository.saveRating`. The user is `@CurrentUser()`, never the body (the schema is strict, so a `userId` is a 400). `saveRating` is one transaction: read the caller's current row (filtered by `companyId`, `applicationId` and `userId`; the upsert's `conflictOn` can only name the global UNIQUE (application, user) key, so it carries no company), call the service's `resolve(previous)` to get the values to store, `Rating.upsert({ create, update, conflictOn: { applicationId, userId } })`, then `ApplicationEvent.create` of type `rated` with `{ previous, current, stage }` (`stage` is the Application's current Stage name, from `job.stages`). The merge rule lives in the service (`mergeCriteria`): start from the stored `criteria`, drop keys sent as `null`, set the numbers, keep every other key, which is how a score for a Criterion the Job dropped survives. Passing `resolve` into the repository keeps the rules in the service while the read and the write stay in one transaction. The service also turns `isUniqueViolation` into a 409, though the upsert's `ON CONFLICT` means the (application, user) key cannot raise it. It answers the saved Rating `{ overall, criteria, updatedAt }` (`criteria` has no `null` values). The detail's read and the board's `rating` are the next two bullets. A spec for "every role can rate" needs the real `ApplicationPolicy` through `AuthorizationModule.forRoot()` (`pipeline.rating.spec.ts`), because the other pipeline specs stub `authorize`.
   - **Detail payload** (`GET .../applications/:applicationId`, `PipelineService.detail`): besides the Application, its `events` and `notes`, it carries `ratings: [{ userId, name, overall, criteria, updatedAt }]`, oldest first, and `ratingSummary: { count, average, criteria }` (`summariseRatings` over those Ratings, so the unrounded mean, `average: null` and `criteria: {}` with none). `flags: ScreeningFlag[]` is the Application's stored flags with their reasons (`[]` for none; members only, interviewers included). `name` is the author's name, or `"Former member"` (with `userId: null`) when the author's user row is gone (a Member who only left the company keeps their name); such a Rating still counts. `criteria` is as stored, so it can hold scores for Criteria the Job no longer uses, and the summary averages them too. Access is unchanged (membership guard plus `jobs.get`, no policy), so interviewers get the same payload. `PipelineRepository.findDetail` returns an `ApplicationDetailRow` whose `ratings` are `RatingRow`s (`userName` null when the user is gone) read in the same `Promise.all` as the events and notes (one query joined to `users`, never one per Rating); the service maps the name and builds the summary, so the rules stay out of the repository. A `rated` event is also in `events` (`data` is `{ previous, current, stage }`). No public payload (`PublicController`, `PublicCompanyController`) has a rating field; `applications.service.spec.ts` ("no Rating reaches the public routes") pins it.
   - **Board payload** (`GET .../jobs/:jobSlug/applications`, `PipelineService.board`): `{ job, columns, highlightedQuestions }`. Same access check as `detail` (membership guard plus `jobs.get`, no policy), so interviewers get all of it. `highlightedQuestions` is the Job's stored `highlightedQuestionKeys` filtered through `highlightableQuestions(latest published form)` (`FormsRepository.findLatestPublished`, from `FormsRepositoryModule`): stale keys and keys on a Question that is no longer highlightable are dropped on every read, the order is the form's, and each is `{ key, label, kind }` with the latest text. Every card (`ApplicationCard`) has `flags: ScreeningFlag[]` (read with the card by `findCards`/`findCardsWithAnswers`, no extra query; `[]` for none) and `highlights: Record<questionKey, Highlight | null>`: the Application's own form version's highlightable Question with that key, as the raw answer tagged by type by `toHighlight` (`@repo/shared`: `{ type: 'text', value }` cut at 200 characters, `{ type: 'number', value }`, `{ type: 'date', value: 'YYYY-MM-DD' }`, `{ type: 'yes_no', value }`, `{ type: 'select', labels }` with the labels from that version's options), or `null` when unanswered or when that version has no such Question. The web app formats and sorts it (`formatHighlight`, `highlightSortValue`), so the value is sent once. Each `highlightedQuestions` entry is `{ key, label, kind }`, the `kind` from the Question's type in the latest published form (`highlightKindOf`). With no keys stored, or none left after filtering, `PipelineRepository.findCards(companyId, jobId)` runs (it `select`s the card columns only, never `answers`) and every card has `highlights: {}`. Otherwise `findCardsWithAnswers(companyId, jobId)` adds `answers` and `formVersionId`, and `findFormFields(companyId, jobId, ids)` reads each distinct version's `fields` once (`id IN (...)`); all three filter by the company and the job, never `include('formVersion')` per row. Only Highlighted answers leave the API this way; the detail does not carry them. **The Average rating on each card (ratings ticket 07):** every card also has `rating: { average, count }` (`CardRating`, `Pick<RatingSummary, 'count' | 'average'>`): the plain mean of the Application's `overall` Ratings, not rounded, `{ average: null, count: 0 }` with none. `PipelineService.board` reads the cards, then `withRatings` makes **one** more query for the whole board, `PipelineRepository.findRatingSummaries(companyId, applicationIds)`: `Rating.where({ companyId }).where((r) => r.applicationId.in(ids)).groupBy('applicationId').aggregate((agg) => ({ count: agg.count(), average: agg.avg('overall') }))` (`avg` over `int2` is typed `number | null`, decoded as a float8, so `13/3` arrives as `4.333333333333333`, the same double as `summariseRatings`). The ids are the cards' own (a `Rating` has no `job_id`), so the query is skipped when the Job has no Applications; with Applications but no Ratings it still runs once and returns nothing. A Rating whose author left (`user_id` NULL) still counts, as in `summariseRatings`. The cards are never `include`d with ratings (a join per card would repeat rows). `CardRow` (the repository's card) has no `rating`: the service adds it, so the repository fakes of `findCards` did not change. Only `{ average, count }` leaves the API on the board, never a Rating's scores or its author.
   - **Files** (ticket 05): `GET .../applications/:id/files` lists an Application's uploaded files (`ApplicationFile`: id, purpose, fieldKey, originalName, mimeType, sizeBytes, durationSeconds; never the storage key) and `GET .../applications/:id/files/:fileId/download` returns `{ url, expiresInSeconds }`, a presigned GET with an attachment disposition and the applicant's original name (`StorageService.createDownloadUrl`, `attachmentDisposition`). Like `detail`, there is no policy call: the membership guard plus `jobs.get` are the access check, so interviewers have the same access as recruiters; `ApplicationPolicy` has no `read` action. The queries live in `PipelineRepository` (`findFiles`, `findFile`), filtered by company, job and Application (and `status = 'uploaded'`), so a file from another Application or company is a 404. Opening a file writes no event. **View** (ticket 06): `GET .../files/:fileId/view` returns the same `{ url, expiresInSeconds }` as a presigned GET with an inline disposition (`inlineDisposition`) and the stored `mimeType` pinned as the response `Content-Type` (`StorageService.createViewUrl`); same access and 404 isolation as download, plus a 400 for a type not in `previewKindOf` (`@repo/shared`, `file-preview.ts`: PDF, DOCX, the image types, video and audio; extend it when the sheet learns to render something new). Never mint an inline link by any other route: the type allowlist is what keeps a hostile file from rendering as a page on the bucket's origin.
   - **Missed must-have on the board and detail** (keyword-match ticket 05, `.scratch/keyword-match/spec.md`): every card has `missedMustHave: boolean`, true only when the Application's stored `application_requirement_results` row has `missed_must_have` (a nice-to-have miss never sets it; no row, which covers an `unreadable`, `failed` or missing CV, is false). `PipelineService.board` reads it with the ratings in `withMarkers` as ONE `PipelineRepository.findMissedMustHaveIds(companyId, jobId)` for the whole board (`select('applicationId')` by company, Job and `missedMustHave`), never per card, and skips it with no Applications. The detail carries `cvState: 'readable' | 'unreadable' | 'failed' | 'none'` (the status of the `cv_texts` row of the Application's CV file, `none` with no CV file or no row; only the `status` column is selected, CV text is never returned) and `requirementCheck: { version, missedMustHave, results: [{ id, text, tier, matched, terms }] } | null`. `findDetail` reads the result row, then the Requirements of `(jobId, version)` from `job_requirement_versions`, so text and tier are those of the checked version (results are in that version's order; a Requirement with keywords but no stored verdict reads as not matched; one without keywords is `matched: null`, "not checked", and `missedMustHave` ignores it). The service returns `requirementCheck: null` unless `cvState` is `readable`, so an unreadable or failed CV never gets a verdict. No policy call (members only, interviewers included). Public payloads carry none of it (`applications.service.spec.ts`, "no Requirement reaches the public routes").
   - **Embedding match on the board and detail** (embedding-match ticket 08, `.scratch/candidate-matching/layer3-spec.md` "Payloads and web"): every card has `matchScore: number | null` (the overall number, for sorting only, never displayed; set only when the row is `scored`) and `matchState: MatchState | null` (`{ status: 'scoring' }` for a `pending` row, `{ status: 'scored' }`, `{ status: 'not_scored', reason }`; **null when the Application has no score row**, which is not a state). `withMarkers` reads them with the ratings and the marker as ONE `PipelineRepository.findMatchScores(companyId, jobId)` for the whole board (`select('applicationId', 'status', 'reason', 'score')` by company and Job, a `Map` by Application id), never per card, skipped with no Applications; `board.spec` counts it with a fake. The detail has `embeddingMatch: { version, state, requirements: [{ id, text, tier, band }] } | null` (null with no row). `findDetail` reads the row and then the Requirements of `(jobId, requirementsVersion)` (`findEmbeddingMatch`, like `findRequirementCheck`), so text and tier are those of the version it was scored against; the service turns each stored score into `band` with `bandOf` (`@repo/shared`, computed on read, no threshold stored) and **drops the score**. `band` is null unless the row is `scored`, and for a Requirement with no stored score. The detail never carries a raw per-Requirement score, the overall number, a vector, a chunk or CV text (`pipeline.detail.spec.ts` pins the exact keys). No policy call (members only, interviewers included). Public payloads carry none of it (`applications.service.spec.ts`, "no embedding-match score reaches the public routes"). The web app's types are `MatchStateView`, `EmbeddingMatchDetailView` in `lib/dal.ts` (mapped field by field; the UI is tickets 09 and 10).

**Audit trail**: every state change (applied, auto-rejected, stage changed, hired/rejected, note added, rated) writes an append-only `ApplicationEvent` **in the same transaction** as the change. Stage names go in `data` so the history stays readable if stages are later renamed or deleted.

## `@repo/shared`

`auth.ts`, `companies.ts`, `jobs.ts` and `applications.ts` hold the request-body schemas. The API validates with them and the web forms reuse them. Rebuild the package after changing them (`pnpm --filter @repo/shared build`), because the API imports its `dist/`.

`form-fields.ts` holds the Zod discriminated union for the ten field types (`short_text`, `long_text`, `single_select`, `multi_select`, `yes_no`, `number`, `date`, `url`, `file`, `repeating_group`) and `parseFormFields()`. `answers.ts` holds `parseAnswers` and `toPublicFields`. These define the JSONB shapes of `form_versions.fields` and `applications.answers`. Field keys and option ids are UUIDs, so relabelling a question doesn't break old answers. Validation failures are returned as `{ ok: false, errors: [{ path, message }] }` and surfaced as `BadRequestException({ message, errors })`.

**Number, date and URL questions.** All three are leaf types with no rules in their config (Screening rules live on the Job; number and date can be screened, URL not yet). `number` config is `{ min, max, integerOnly }` (answer: a finite JSON number; `0` is an answer), `date` is `{ min, max }` as ISO `YYYY-MM-DD` (answer: an ISO string; validated with `Temporal.PlainDate.from(..., { overflow: 'reject' })` and a round trip, in `dates.ts`), `url` has no config (answer: trimmed, at most 2,048 characters, `http:` or `https:` only). `@repo/shared` uses plain `Temporal`, never a polyfill: Node >= 26 supplies it, the web app loads a polyfill, and the package's `lib` has `"esnext.temporal"` for the types (add it to any package that type-checks shared's source).

**Highlighted questions and answer text.** `highlights.ts` holds the rules both the picker and the API run: `HIGHLIGHT_LIMIT` (3), `highlightableQuestions(fields)` (top-level Questions of the eight single-answer types, an allowlist, in form order; never a file Question, a Repeating group or a sub-question), `isHighlightable(fields, key)`, `highlightedQuestionKeysSchema` (at most 3 UUIDs, no repeats; wrapped by `saveHighlightedQuestionsSchema` in `jobs.ts`) and `checkHighlightKeys(keys, fields)` (one `<index>` error per key not on the form or not highlightable). `answer-text.ts` holds the text rules for one leaf answer: `formatAnswerText` (option labels, `Unknown option`, `Yes`/`No`, `String(number)` so `0` is an answer, the long date via `formatIsoDate` in `dates.ts`; a multi-select as a list), used by the web sheet, and `formatHighlightText` (the same text on one line: a multi-select joined with `", "`, a link as trimmed plain text, `null` for no answer or blank text (`isBlankAnswer`; `formatAnswerText` keeps blank text as stored, so the sheet is unchanged), cut at `HIGHLIGHT_MAX_CHARACTERS` (200) code points plus `…`), which `toHighlight` reuses for text. `toHighlight(field, value)` builds the tagged `Highlight` the board payload sends (a number, date and yes/no stay raw; a select becomes labels), `highlightKindOf(field)` gives a column's kind, and `highlight-display.ts` holds what the web app does with it: `formatHighlight`, `highlightSortValue(highlight, kind)` and `compareHighlightSort`.

**Ratings and Criteria** (`.scratch/ratings/spec.md`). `rating-criteria.ts` holds the catalog `RATING_CRITERIA` (`{ key, label }` for `technical_skills`, `problem_solving`, `communication`, `culture_fit`, `leadership`, `relevant_experience`; also `RATING_CRITERION_KEYS`, `RatingCriterionKey`), `RATING_CRITERIA_LIMIT` (5), `RATING_MIN`/`RATING_MAX` (1 and 5) and `ratingCriteriaKeysSchema` (at most 5 catalog keys, no repeats; wrapped by `saveRatingCriteriaSchema` in `jobs.ts`). The catalog is **append-only** like `PRESET_KEY_TYPES`: never remove or rename a key, or a stored Job selection or Rating could no longer be read (`rating-criteria.test.ts` pins the exact keys). `ratings.ts` holds `saveRatingSchema` (`overall` an integer 1 to 5, required; optional `criteria`, catalog key to an integer 1 to 5 or `null` to clear; strict, so no `userId`), `checkRatingCriteria(criteria, selectedKeys)` (`{ ok: true, criteria }` or `{ ok: false, errors: [{ path: '<criterionKey>' }] }` for each key not in the Job's selection, a `null` included; the service prefixes the path with `criteria.`), `FORMER_MEMBER_NAME` ("Former member": the API's name for a Rating whose author is gone, also the web's for a history line or Note it cannot attribute), `RatingValues` (`{ overall, criteria: Record<string, number> }`, a Rating's scores as stored, never `null`; a `type`, not an `interface`, because an interface is not assignable to the JSON the `rated` event's `data` takes; the API's `RatingView`, `RatingRow` and `SavedRating` and the web's `RatingView` build on it), and `summariseRatings(ratings)` (`{ count, average, criteria }`: `average` is the unrounded mean of `overall`, `null` with no Ratings; `criteria` maps a key to `{ count, average }` over the Members who scored it, and a Criterion nobody scored is absent).

**Repeating groups and Preset keys (ADR-0004).** A `repeating_group` question holds its sub-questions at `config.fields` (at least one, only the leaf types `short_text`, `long_text`, `single_select`, `multi_select`, `yes_no`, `number`, `date`, `url`: `LeafFormField`) and `config.maxEntries` (1 to 10). It counts as one question toward `MAX_FIELDS`. Sub-questions go through the same per-question function as top-level ones, so a new leaf type works inside groups with no group-specific code; sub-question keys are unique across the whole form. The answer is an array of Entries (`Entry`, objects keyed by sub-question key; `AnswerValue` is recursive for this). `parseAnswers` drops fully blank Entries, applies each sub-question's `required` to an Entry that has any answer, rejects unknown keys and more than `maxEntries`, and reports errors at `<groupKey>.<index>.<childKey>` (the index is the Entry's position in the submitted array). `maxEntries` counts the Entries left after blanks are dropped, so blank extras are not an error. Screening rules ignore groups; `toPublicFields` passes them through whole. `answers.ts` also exports the two small rules the apply page and candidate sheet reuse: `isBlankAnswer` (missing, `null`, spaces-only text or an empty list; `false` is an answer) and `isPlainObject` (an Entry, as opposed to `null`, a list or a primitive). Every question may carry a `presetKey`, optional and nullable because stored forms lack it. `preset-keys.ts` holds the catalog `PRESET_KEY_TYPES` (key to required question type; also `PRESET_KEYS`, `PresetKey`). The catalog checks a key against its question type only, not its parent group. It is **append-only**: never remove a key or change its type, or an old published form could no longer be loaded or its draft edited. The one exception is the one-time retyping of `education.start_year`/`education.end_year` (now `number`) and `experience.start_date`/`experience.end_date` (now `date`), made because nothing had been published (ADR-0004 note; header of `preset-keys.ts`); do not repeat it, add new keys instead. `parseFormFields` refuses an unknown key, a key on the wrong type, and a repeated key within one scope (once among top-level questions, once inside each group). The full Preset definitions (labels, help text, options, limits) are not in the shared package; they live in the web app (`form-builder/presets.ts`). The rules and the tests (`form-fields.test.ts`, `answers.test.ts`, `preset-keys.test.ts`) are the one automated seam for this feature; see `docs/db-schema.md` §4.1 and §4.2 for the shapes.
