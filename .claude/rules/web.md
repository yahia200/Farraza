# Web architecture

Loaded when you work in `apps/web`. The shared facts, docs table, and commands are in the root `CLAUDE.md`. Read `apps/web/AGENTS.md` (the Next.js 16 block) and the version-matched docs in `apps/web/node_modules/next/dist/docs/` before writing web code.

- **Reach for shadcn first when building UI.** Before hand-rolling any UI primitive (button, dialog, table, select, toast, form field, dropdown, etc.), check `components/ui/` for one that already exists, then the shadcn registry (`shadcn` 4.21.3 CLI, `@shadcn/react` on `@base-ui/react`; https://ui.shadcn.com/docs). Add a missing one with `pnpm --filter web exec shadcn add <name>` rather than writing it from scratch. Build a custom component **only when no shadcn component fits** — and when you do, say why none fit. Don't bend the UI to fit a component, and don't fork a component's internals when a prop or composition would do. Before re-adding with `shadcn add --overwrite`, check the "Generated shadcn files we changed" list below so local edits aren't lost.
- **Next.js is a backend for the frontend.** The browser never calls the API. Server Actions (`app/actions/`) and the DAL (`lib/dal.ts`) call it from the server through `lib/api.ts`, which reads `API_URL` from `apps/web/.env.local` and forwards the session cookie.
  - The API's `__Host-sid` cookie is relayed onto the web origin with `relaySessionCookie()`.
  - Docs: `02-guides/backend-for-frontend.md`, `03-api-reference/04-functions/cookies.md`.
- **The DAL is the only place that reads "who is signed in".** `getCurrentUser()` and `getMyCompanies()` use `'use cache: private'` and redirect to `/sign-in` on 401. Any component that calls them must render inside `<Suspense>` (`cacheComponents` is on).
  - Any action that changes the session or memberships must call `revalidatePath('/', 'layout')` before redirecting, or the private cache serves stale data.
  - Docs: `02-guides/authentication-with-cache-components.md`.
- **Route groups:**
  - `(marketing)`: the landing page, and the only place with the floating `NavBar`. It always renders light: its layout wraps everything in `.light`, which re-declares the light tokens (`:root, .light` in `globals.css`) and is excluded from the `dark:` variant (`&:is(.dark *):not(.light *)`). next-themes' `forcedTheme` doesn't fit here: a nested `ThemeProvider` is ignored, and reading `usePathname()` in the root layout would suspend on dynamic routes.
    - "Four steps to hire" (`components/landing/`) is a stack of cards that pile up while scrolling: CSS `position: sticky` pins each card, and Motion only shrinks the covered ones (off under `useReducedMotion()`). `CardStack` shares one `useScroll` through context; the card content stays server-rendered children. Sticky breaks inside an ancestor with `overflow` hidden/auto/scroll (the Hero has `overflow-hidden`), so keep the section a sibling of the Hero.
    - "More than a pipeline" (`components/landing/features-section.tsx`) follows it: a bento grid of what the steps don't cover (team roles, careers page, board or table). One column on phones. From `md`, three columns of rows `--tile-height` tall (`auto-rows-(--tile-height)`; 26rem, 30rem from `xl`): roles and the candidates table are two columns wide on the left, and the careers phone shot spans both rows on the right. Spans are in `tilePlacement`. The array order is both the phone order and the grid's auto-placement order. Its screenshots in `public/landing/` are crops of `.scratch/landing/screenshots/` (WebP, 1600 px wide, phone shot 900 px), with `width`/`height` set to each file's real pixels. The two table shots (`team-roles`, `pipeline-table`) are the table alone: cropped just inside its 2px border, with the leftover rounded-corner arcs painted white, so the tile's own `ring` and `rounded-tl-2xl` act as the table's frame. After replacing an image under the same name, delete `apps/web/.next/dev/cache/images`: the optimizer keeps each size for hours and can't be invalidated (`03-api-reference/02-components/image.md`, `minimumCacheTTL`).
    - The closing call to action (`components/landing/cta-section.tsx`) comes last: one `Card` split in two, the heading and the "Take a step" sign-up link on the left and the Climb figure on the right (stacked, figure first, on phones). Climb is a Hairline drawing: a flight of five steps, one per default stage from Applied to Hired, and a pawn that hops to the step under the pointer. It runs on the Hairline kernel vendored as `components/landing/hairline/kernel.js`, which is the hairline-create skill's `kernel.js`, unchanged except for a closing `export default HL`. The `@lucasmarkes/hairline` package can't mount a custom figure. `climb-figure.tsx` mounts it in an effect, the way the package's React components do, plays its tour until a pointer arrives, shows no read-out (the stage names go to a plain object), takes a `palette` (`plate`, `hi`, `edge`, `mid`, `lo`, `strokeWidth`) that sets the kernel's `--hairline-*` variables on its wrapper (the CTA's, in `cta-section.tsx`, fills the plates primary-500). `plate` only fills the solids, so the box around the drawing stays transparent unless `className` gives it a background; keep `plate` opaque, because nearer solids hide farther ones with their fill. It also pins `data-hairline-theme="light"` (otherwise the kernel's CSS follows an `html.dark`). The figure's source of truth is `.scratch/landing/hairline/climb.js`, checked with the skill's `look.mjs`. `components/landing/hairline/climb.js` has the same body, with an import and an `export const climb` in place of the `hairline({...})` call, so copy any change across.
  - `(auth)`: sign-in, sign-up, verify-email, forgot-password and reset-password. The layout centers and sizes the column; each page renders `AuthCard` (`components/auth/auth-card.tsx`: title as the page's `<h1>`, description, content, optional footer whose links it styles). Change the auth look there, not in `components/ui/card.tsx`.
  - `(onboarding)`: `/onboarding`.
  - `(dashboard)`: the shadcn sidebar layout. Besides `/dashboard/…` it holds `/companies/new`, the two-step "Add company" page (name, then optional logo and color), which is linked from the company switcher. It isn't at `/dashboard/new` because "new" is a valid company slug.
  - `/dashboard/settings` is the per-user settings page (Appearance and Account tabs, `components/settings/`), linked from the account menu (`NavUser`). A fixed segment beside `/dashboard/[companySlug]` hides any company with that slug, so `settings` is in `RESERVED_COMPANY_SLUGS`; reserve any new fixed segment under `/dashboard` the same way. It has no `companySlug`, so the sidebar keeps the company you were last in: `CompanySwitcher` resolves the company (URL slug, else the remembered one, else your first) and reports it to `ActiveCompanyProvider` (`components/dashboard/active-company.tsx`, inside `AppSidebar`), and `NavMain` links to it (until it is known, `NavMain` shows the items without links; for a user with no company, nothing). The memory lasts while the `(dashboard)` layout stays mounted; a full load of `/dashboard/settings` starts from your first company.
- **Company pages** live at `/dashboard/[companySlug]/…`, because top-level `/{company}/{job}` is reserved for public apply pages (`docs/db-schema.md`). Every company page wraps its content in `CompanyPage` (`components/dashboard/company-page.tsx`).
  - `CompanyPage` awaits `params` inside `<Suspense>` and calls `getCompany(slug)`.
  - That call doubles as the membership check: the API answers 404 to non-members, so they get `notFound()`. The status stays 200 after streaming, with `noindex` (`03-api-reference/04-functions/not-found.md`).
- **Gating:** there is no `proxy.ts`. Pages enforce routing themselves:
  - Signed-out users are redirected to `/sign-in` by the DAL.
  - `/dashboard` redirects to your first company, or to `/onboarding` if you have none. `/onboarding` sends users who have a company back to `/dashboard`.
  - Sign-up goes to `/onboarding`. Creating a company redirects to that company's dashboard.
- **Pitfalls hit while building the dashboard:**
  - **Keep the sidebar frame (`AppSidebar`) out of `<Suspense>`.** On phones the provider switches to the mobile sheet right after hydrating, and a boundary that hydrates later no longer matches the server's desktop HTML. Pass the data parts in as async Server Component slots, each in its own boundary (see `app/(dashboard)/layout.tsx`).
  - **A Server Component can't use a non-component value exported from a `'use client'` module.** It gets a client reference, not the value. Put shared constants in plain modules, like `components/dashboard/nav-items.ts`.
  - **Under `cacheComponents`, `useParams()` suspends for dynamic segments**, so wrap components that use it in `<Suspense>` (`03-api-reference/04-functions/use-params.md`).
  - **No `Math.random()` in anything prerendered**, including Suspense fallbacks. That's why we don't use shadcn's `SidebarMenuSkeleton`.
- **Sidebar open/collapsed state is restored from shadcn's `sidebar_state` cookie without reading it on the server** (that would push the sidebar behind `<Suspense>`). See `components/dashboard/persistent-sidebar.tsx`:
  - An inline script fixes the DOM before first paint.
  - A lazy `useState` reads the same cookie, so hydration matches.
  - Pattern: `02-guides/preventing-flash-before-hydration.md`, "Syncing with React state".
  - If you change `collapsible` on `<Sidebar>`, use `SIDEBAR_COLLAPSIBLE` so the script stays in sync.
- **Members (`/dashboard/[companySlug]/members`):** a data table following shadcn's data-table guide (https://ui.shadcn.com/docs/components/base/data-table), built on **TanStack Table v9**. v9's API differs from v8:
  - `useTable` instead of `useReactTable`.
  - Features and row models are registered with `tableFeatures({...})`.
  - Columns use `createColumnHelper<Features, Row>()`, and cells render with `<table.FlexRender>`.
  - `Column<Features, Row, Value>` needs its value type.
  - Read the `.d.ts` files in `node_modules/@tanstack/table-core` before changing it.
  - The table's typed `meta` (the `tableMeta` slot) tells the cells who is viewing.
- **Member and job permissions live in `packages/shared/src/members.ts`** (`canManageJobs` included). The API's `MemberPolicy` and `JobPolicy` and the web UI all use them, so change the rules there.
- **Data tables:** `components/data-table/data-table.tsx` (`DataTable`, `DataTableSortButton`, `DataTableColumnMeta`) only renders a table instance. Each feature keeps its own `data-table-features.ts` (v9 `tableFeatures`), `columns.tsx` and a `useTable` call; see members and jobs.
- **Jobs:**
  - The list at `/dashboard/[companySlug]/jobs` has a status filter (`ToggleGroup`, whose Base UI value is an array).
  - Each job lives at `/dashboard/[companySlug]/jobs/[jobSlug]`. Its `layout.tsx` holds the header (status and open/close) and link-tabs (`JobTabs`) to Overview, `/form` and `/candidates`. The pipeline (`/candidates`) is the board and table of candidates; see "Pipeline board" below.
  - Pages use `JobPage` (like `CompanyPage`) to await params and load the company and job.
- **Pipeline board (`/jobs/[jobSlug]/candidates?view=board`, `components/dashboard/candidates/`):**
  - `PipelineBoard` is a client component seeded with the server's columns. `useOptimistic` with `applyMove` from `@repo/shared` as the reducer shows a move at once; `moveApplication` returns failures (no throw), so when the transition ends the board falls back to the server's columns (a failed move snaps back) and the board toasts the failure. The action revalidates on 404/409, so a stale view corrects itself.
  - Two ways to move a card, both only when `canMoveApplications(role)` (the page passes a `canMove` boolean): the `MoveToStageSelect` on each card (keyboard, touch, phone tabs) and drag-and-drop with `@atlaskit/pragmatic-drag-and-drop` (ADR-0001). Use the 4.x import paths (`.../adapter/element-adapter`, `.../utils/combine`); the library's website still shows the deprecated ones.
  - Drag is desktop-pointer only (`hooks/use-fine-pointer.ts`, `(hover: hover) and (pointer: fine)`), and only on the desktop columns, never the phone tabs. Register `draggable()` / `dropTargetForElements()` / `monitorForElements()` only inside effects, and register `draggable()` conditionally: `canDrag: () => false` would cancel drags page-wide.
  - The card is a div with the link and the Select as siblings (a control can't sit inside a link). The link is `draggable={false}`, otherwise the browser drags the anchor instead of the card, and the drag handle is the link, so pressing the Select never starts a drag. A drag fires no click, so it doesn't open the detail sheet.
  - A drop is handled in one monitor in `PipelineBoard`; columns only highlight themselves. The column a card came from isn't a drop target, and `move()` also ignores a same-stage move (no API call, no optimistic update).
- **Form builder (`/jobs/[jobSlug]/form`, `components/dashboard/jobs/form-builder/`):**
  - One React Hook Form for the whole list: `useFieldArray({ name: 'fields' })`, validated by `zodResolver(z.object({ fields: formFieldsSchema }))`, the same schema the API uses.
  - "Save draft" PUTs the draft and "Publish" POSTs publish, saving unsaved changes first (`app/actions/forms.ts`). API errors have paths relative to the list (`"2.config.options"`), so they're applied as `fields.${path}`.
  - The CV setting (`cvMode`: off, optional, required; ADR-0002) is a second RHF value beside `fields`, edited in `CvCard` above the questions (shadcn `ToggleGroup`; it has no `readOnly` prop, so read-only viewers get a group that ignores changes) and saved/published together with the questions. A job with no form yet starts at `DEFAULT_CV_MODE` (`optional`); the backup stores `cvMode` too (older backups without it mean "unchanged"). The public job payload carries `cvMode`, which the apply page turns into its first step.
  - The page keys `FormBuilder` on the draft's `updatedAt` and the published version, so a save remounts it with fresh default values.
  - `field-types.ts` lists the builder types, "File upload" included. A file question's config (kinds, size, `maxDurationSeconds`) is edited by `FileConfigEditor` (`file-config-editor.tsx`): one checkbox per kind, a size input, and, only while video or audio is ticked (`kindsNeedDuration`), a required length limit in seconds with a words preview (`formatDurationInWords`); unticking the last of them sets it back to null. The missing-limit error comes from `parseFormFields` on `config.maxDurationSeconds` and shows under that field. While the size still equals the suggestion for the old kinds (`suggestedMaxSizeMb`: 10 MB documents and images, 25 MB audio, 100 MB video; the largest when kinds are mixed) it follows the suggestion as kinds change. New file questions start as documents, 10 MB.
  - **Number, Date and Link (URL) questions (question-types ticket 02).** `FIELD_TYPES` has an entry for each (`HashIcon`, `CalendarIcon`, `LinkIcon`; the URL one is labelled "Link (URL)"), so the "Add question" menu lists them; `newField` starts them as Number `{ min: null, max: null, integerOnly: false }`, Date `{ min: null, max: null }`, URL `{}`. `limits-config-editor.tsx` has `NumberConfigEditor` (Minimum, Maximum, "Whole numbers only" switch) and `DateConfigEditor` (Earliest/Latest, native `<input type="date">`, whose value is already the stored `YYYY-MM-DD`); an empty box is `null`. The shared rule's "can't be more than" message is on `config.min` and shows under Minimum / Earliest date. A URL card has only the basics, and none of the three has an auto-reject control. The builder has no type change, so nothing to keep consistent there. **Testing the builder with a second login:** the `__Host-sid` cookie is shared by every `localhost` port, so use `http://<name>.localhost:3000` (next dev allows `localhost` subdomains; `127.0.0.1` is blocked and the page never hydrates) for a separate session.
  - Choice options are a controlled list (`OptionsEditor`), not a nested `useFieldArray`: RHF writes its own `id` on rows, and options already have a real `id` that auto-reject rules point at.
  - Unsaved changes are backed up to localStorage (`use-form-backup.ts`, read with `useSyncExternalStore`). If the backup differs from the saved form on load, editing is locked until the user restores or discards it.
  - Paths into type-specific config go through `at(prefix, 'config.x')` in `field-types.ts`, cast once, because the question types are a union. `prefix` is where the question sits (`fields.2`, or `fields.2.config.fields.0` for a sub-question of a group), so the same code edits a card and a group's sub-question. `QuestionBasics` (`question-basics.tsx`: text, help text, required, plus a line for `key`/`presetKey` errors, which have no control) is that shared part; it also exports `COLLAPSIBLE_PANEL_CLASS`, the height animation below. Its Controllers read `input.value` as `unknown` (the generic path's type is a union), so they coerce (`String(...)`, `=== true`).
  - **Presets and the group card (ADR-0004).** The "Add question" menu has a second group, "Presets", below the question types (a `DropdownMenuSeparator`, and its own `DropdownMenuGroup` because `DropdownMenuLabel` needs one). The definitions live in `presets.ts` (`PRESETS`, each with `presetKey`, `menuLabel`, `icon`, `build()`), beside `newField`; `@repo/shared` only holds the catalog of keys. `build()` makes a fresh copy every time (new `crypto.randomUUID()` keys and option ids, every question tagged with its Preset key); the form keeps no link to the definition. The menu item takes Base UI's `disabled` while some question on the form has that `presetKey` (the schema allows a Preset once per form), and it comes back when the group is deleted. A group counts as one question toward `MAX_FIELDS`, so the trigger's limit is unchanged. There is no blank-group option, and no way to add, remove or reorder sub-questions, change their types or edit their options.
  - The group's card is `QuestionCard` with a `GroupEditor` (`group-editor.tsx`) body: `maxEntries` (number input, shared message "Set an entry limit from 1 to 10."), then one collapsible row per sub-question (`SubQuestionRow`) that edits text, help text and required through `QuestionBasics` and shows the type and, for choices, the fixed options as plain text. A sub-question row opens itself on an error with the same adjust-state-during-render rule as the card (`hasErrorAt(errors, path)`), so a bad sub-question opens the group and then its own row. API error paths such as `3.config.fields.1.label` become `fields.3.config.fields.1.label` and land on the same control. Read-only and `disabled` are passed down to every control, as for the other cards. The group is saved, published and backed up like any question (the backup is JSON of the whole `fields` array).
  - **Phone width.** A `<fieldset>` has `min-width: min-content` by default, so a card header that can't shrink widens the whole question list past the screen; the list's fieldset in `form-builder.tsx` has `min-w-0` for that, and the group's "Up to N entries" badge is `hidden sm:inline-flex`, so the label and the move/delete buttons fit at 375px. Checked at 375px: the builder and the apply page have no horizontal scroll.
  - A question with an error opens itself by adjusting state during render (`if (hasError && !open) setOpen(true)`), so it stays open once the error is fixed (https://react.dev/learn/you-might-not-need-an-effect#adjusting-some-state-when-a-prop-changes).
  - New questions open by comparing `row.key` from `useFieldArray`; `useWatch` values lag one render behind `append`.
  - People who can't manage jobs (interviewers) see the builder **read-only**: cards still open, controls get `readOnly` (full contrast, focusable), and the move/delete/add buttons are hidden. `disabled` is only for the temporary lock while the restore-backup banner shows. Both are set on each control, because Base UI's Switch, Checkbox and Select ignore a native `<fieldset disabled>`, and a disabled fieldset also disables the cards' expand buttons. Controllers don't get RHF's `disabled`, which would also drop the field from validation and submitted data.
  - Cards animate open and closed with the height transition from Base UI's Collapsible docs (`docs/react/components/collapsible.md`). The panel's padding and border sit on an inner div, because they would still show at `height: 0`. Base UI resets the height to `auto` after opening, so content that grows later isn't clipped; in the hidden browser pane that only happens once frames are drawn.
- **`html` has `scrollbar-gutter: stable`** (`globals.css`), so the page doesn't shift when popups lock scrolling. Base UI's scroll lock keeps that value instead of adding padding.
- **Reset dialogs and forms before navigating away from them with `router.push`.** Next.js keeps the previous page mounted with its React state (Activity), so pressing Back otherwise reopens the dialog with the old values (`02-guides/preserving-ui-state.md`).
  - Reset in the submit handler, as in `NewJobDialog`.
  - Or, to avoid a flash, reset in a `useLayoutEffect` cleanup, which runs as the page is hidden (as in `AddCompanyWizard`).
- **Keep element `id`s unique across the app.** Next.js 16 keeps recently visited routes mounted but hidden, so the same id on two pages, such as a dialog and a form, can break `<label for>`.
- Dates shown in the UI are formatted on the server with `formatDate` (`lib/format.ts`).
- **`Temporal` polyfill.** `@repo/shared` date checks (`dates.ts`) use the global `Temporal` and never import a polyfill; Node >= 26 has it natively, browsers may not. `apps/web/instrumentation-client.ts` imports `temporal-polyfill/global` (installs only when `Temporal` is missing, so native wins) and `temporal-polyfill/types/global` (global types; web is on TypeScript 5.9, which has no `esnext.temporal` lib, so drop the second import if web moves to TypeScript >= 6 with `lib: ["esnext"]`). Next runs that file on the client before hydration (`03-api-reference/03-file-conventions/instrumentation-client.md`, `03-architecture/supported-browsers.md` "Custom Polyfills"); the server needs nothing. Polyfill docs: `node_modules/temporal-polyfill/README.md`.
- **Toasts:** shadcn's `toast` (Base UI Toast, no extra package). Call `toast.add({ type, title, description })` from client code; the `<Toaster />` is in the dashboard layout.
- **Base UI gotchas:**
  - `DropdownMenuLabel` (`Menu.GroupLabel`) must sit inside a `DropdownMenuGroup`, or opening the menu crashes.
  - `AlertDialogAction` is a plain Button and doesn't close the dialog; that's on purpose, so a pending action can keep it open.
  - Radio menu items stay open unless given `closeOnClick`.
  - `<Select>` needs `items` to show labels instead of raw values.
- **Generated shadcn files we changed** (check these before running `shadcn add --overwrite`):
  - `components/ui/dropdown-menu.tsx` gained `DropdownMenuLinkItem`, which wraps Base UI's `Menu.LinkItem`.
  - `components/ui/button.tsx`: the `secondary` variant is a solid brand-accent fill (`bg-brand-accent text-brand-accent-foreground`, `hover:/80` like `default`) instead of shadcn's grey `bg-secondary`. The `--secondary` token is unchanged, so badges and other `bg-secondary` surfaces keep the grey.
  - `components/ui/card.tsx`: `Card` gained a `ghost` prop (no background, shadow or ring; used by the auth and settings cards). It removes the ring with `ring-0`, because `cn` keeps the base's `dark:ring-foreground/10` beside a `ring-transparent`.
  - `components/ui/badge.tsx` gained `success` and `warning` variants (solid fill with the dark `-foreground` text, which reads in both themes) and exports the `BadgeVariant` type.
  - `components/ui/toast.tsx` colors the success and warning icons (`text-success`, `text-warning`), like the error icon's `text-destructive`.
  - `hooks/use-mobile.ts` uses `useSyncExternalStore` instead of calling `setState` in an effect.
- **Testing in the hidden browser pane:** React's streamed reveals are scheduled with `requestAnimationFrame`, which doesn't run while the page isn't drawn. If Suspense content looks stuck, take a screenshot (which forces a draw) before concluding it's a bug.
- **Forms:** React Hook Form with `zodResolver(<schema from @repo/shared>)` and shadcn `Field`/`FieldError` (https://ui.shadcn.com/docs/forms/react-hook-form).
  - `onSubmit` calls a Server Action, which re-validates and returns `ActionFailure<Field>` on failure or redirects on success.
  - `applyActionFailure()` puts server errors into the form.
  - `failureFromResponse()` maps API errors (400 `errors[]` to fields, 429, and per-action overrides such as 409).
- **Public apply page (`app/(public)/[companySlug]/[jobSlug]`, `components/apply/`):**
  - Fixed routes win over this one, so company slugs in `RESERVED_COMPANY_SLUGS` (`@repo/shared`) are never handed out. Add new top-level routes there (and new fixed segments directly under `/dashboard`).
  - Data comes from `getPublicJob` (`lib/public-jobs.ts`): `'use cache: remote'` shared by all visitors (plain `'use cache'` lives in memory, which serverless instances don't share; on Vercel the remote cache is its Runtime Cache), without the session cookie, tagged per job and per company, with `cacheLife('minutes')` as a fallback. Actions that change what applicants see call `expirePublicJob` (`updateTag`): form publish, job edit/open/close, company settings.
  - The form uses React Hook Form with a custom resolver (`apply-values.ts`) that runs `submitApplicationSchema` (contact) and `parseAnswers` (answers), the API's own checks. Unanswered questions are left out of `answers`.
  - It's shown with shadcn's **Questionnaire** (`components/ui/questionnaire.tsx`, on `@shadcn/react`; https://ui.shadcn.com/docs/components/base/questionnaire, API https://ui.shadcn.com/docs/react/questionnaire): one question per step, name/email/phone first, letter shortcuts for choices.
    - RHF owns the values; every choice and input is controlled, and all changes go through `answer()` in `apply-form.tsx`.
    - The questionnaire is controlled (`item`/`onItemChange`): moving forward runs `form.trigger()` on the current step; failed submits and server errors jump to the first step with an error.
    - Its built-in check only knows "answered or not" and its default message talks about choosing, so text steps pass their own `QuestionnaireError` text.
    - Long answers use `QuestionnaireInput` with `render={<textarea />}`; its `type` has no `file`, so uploads would need a custom control inside a step.
    - The `items` list given to the root must match what the steps render, including disabled choices (multiple-choice limit). Locked options are tracked as a string in `answer()`; watching all answers from `ApplyForm` caused a render loop, and so did listing `disabled: false` on options (@shadcn/react 0.3.1).
  - `utm_source` from the link is sent as `source` only if it's 1–100 characters (`app/actions/applications.ts`). The `website` honeypot is an off-screen, `aria-hidden` input; the API fakes success when it's filled.
  - Applicants' answers aren't saved locally (personal data on possibly shared devices).
  - **CV step (`cv-step.tsx`):** when `cvMode` isn't `off`, a `cvFileId` step comes first (named like the API's request property, so a server error with that path finds it); optional means Skip, required blocks Next. The questionnaire's `Input` has no file type, so `CvStep` is a custom control inside a normal `QuestionnaireItem`: a visually hidden native file input (keyboard focusable; its label is the button) plus a read-only `sr-only` `QuestionnaireInput` that mirrors the file id, because the questionnaire only counts a step as answered when one of its own controls has a value. Choosing a file checks it with `checkCvFile` from `@repo/shared` (no request if it fails), calls the `createUpload` Server Action for a presigned URL, then `putFile` (`lib/put-file.ts`, XHR for upload progress) PUTs the bytes to the bucket with the exact `Content-Type` the API returned. Only the id goes into the form (`cvFileId`); the `File` stays in component state. While sending, `ApplyForm`'s `uploading` flag disables Skip, Next and Send and `changeStep` refuses to move. A 409 with `errors` on `cvFileId` clears the id and sends the applicant back to the step. Presigned URLs are never cached: `getPublicJob` carries only `cvMode`.
- **Upload control and Attachment steps (ticket 07):** the picker described under "CV step" (file input, browser-side check, `createUpload` action, `putFile`, progress, retry, remove, the `sr-only` mirror input) lives in `upload-control.tsx` (`UploadControl`), which `CvStep` and `AttachmentStep` share; it takes `target` (`{ purpose: 'cv' }` or `{ purpose: 'answer', fieldKey }`), `accept`, and a `check(file)` returning a `FieldError | null` (`checkCvFile`, or `checkAttachmentFile(field.config, file)`). `AttachmentStep` (`attachment-step.tsx`) is the step for a `file` question: label (with "(optional)"), help text, `attachmentHint(config)`, answer = the file id at `answers.<key>` (`ApplyForm` renders it instead of `QuestionStep` for `type === 'file'`). `ApplyForm` tracks which steps are sending in `uploadingSteps` (each control reports `onBusyChange(busy)` for its own step name); any one disables Skip/Next/Send and `changeStep`. A server error whose path is a file question's key (400 bytes mismatch, 409 conflict) clears that answer and sends the applicant back to its step, like `cvFileId`. **Video and audio (ticket 09):** when `check` (`checkAttachmentFile`) passes type and size but returns a `durationSeconds` error, `UploadControl` reads the length from the file with `readMediaDuration` (`lib/media-duration.ts`: an off-DOM `<video>`/`<audio>`, an object URL, `loadedmetadata`; resolves null on error, timeout or abort), rounds it up with `declaredDuration` and checks again, so an over-long file is refused before any request with the allowed length in the message. A file whose length cannot be read is refused too ("We couldn't read how long this file is"): the server cannot re-measure, so accepting it would let the limit be skipped. The declared `durationSeconds` goes in the create-upload request. All steps stay mounted (hidden) while the questionnaire moves, so an upload state survives going back and forth.
  - **Group step (ticket 04, ADR-0004).** A `repeating_group` question is one step, `GroupStep` (`group-step.tsx`, rendered by `ApplyForm` instead of `QuestionStep`), never a step per Entry or per sub-question: the `items` list is `{ name: field.key, required }` with no `choices`, like the CV and file steps, so it can't change while the applicant adds or removes cards (a changing list has caused render loops here). Same technique as `UploadControl`: a read-only `sr-only` `QuestionnaireInput` mirrors `'answered'` when some card has an answer (`entryHasAnswer`), because the questionnaire only counts a step as answered through its own controls; a required group with only blank cards is therefore "unanswered" and blocks Next, an optional one is skipped with Skip. The value at `answers.<groupKey>` is the list of cards (`EntryInput[]`, blanks included, keyed by sub-question key); every change goes through `answer()` with the whole list, so a step showing an error re-checks. `emptyValues` gives a required group one blank card and an optional group none; "Add another" is disabled at `config.maxEntries`. `GroupCards` keeps only a list of numeric card ids in state (React keys, so removing card 1 doesn't hand its controls to card 2); the values stay in the form. The controls inside a card are plain shadcn ones (`Input`, `Textarea`, `RadioGroup`, `Checkbox`, wrapped in a `Label`/`FieldLabel` as in Base UI's radio and checkbox docs), not `QuestionnaireChoice`, so the questionnaire's letter shortcuts and the page-wide `lockedOptions` never see them; a multiple-choice limit is read from that card's own selection with `isLockedOption(child, entry[child.key], optionId)`. The cards' container stops `keydown` from reaching the questionnaire's handler (Enter would go to the next step or, from a plain text input, submit the application; arrows would change step) and cancels Enter in single-line inputs. `compactAnswers` drops each card's blanks but keeps every card, as `{}` when blank, in order, and leaves the group out when no card has an answer, so the answers are exactly what `parseAnswers` takes (no client-only format) and its error index `<group>.<index>.<child>` is the card's position on the page. Errors: the resolver's flat paths become nested RHF errors (`@hookform/resolvers` `toNestErrors`), which `GroupStep` reads from `fieldState.error` by card index and sub-question key (a message on the group itself is `message`, or `root` when cards have errors too). `ApplyForm.stepOf()` maps a server path such as `<group>.1.<child>` to the group's step, `setError`s the full path so the right input in the right card is marked, and sends the applicant back to that step. **Don't use shadcn's `FieldGroup` inside a card:** it is a size container (`@container`, `container-type: inline-size`), and in Chrome a card collapsed to zero height every time an error under one of its inputs cleared; a plain flex column does the job. **Known gaps (ticket 07 pass):** after an error, focus stays on the Next/Send button (client errors) or falls to the page (server errors) instead of moving to the invalid input in its card, though the invalid input is marked and its message shown; and an optional single-choice sub-question inside a card cannot be cleared once chosen (the applicant removes the card). No shipped Preset has an optional single choice.
  - **Number, Date and URL steps (question-types ticket 03).** `QuestionStep` renders them with `QuestionnaireInput` of `type` `number`, `date`, `url` (the questionnaire's `Input` accepts those types: `node_modules/@shadcn/react/dist/questionnaire/index.d.ts`), and `SubQuestionControl` in `group-step.tsx` with the shadcn `Input` of the same types, so a group's Entry card needs no group-specific code. The form holds the box's **text** (`''` when blank; `blankLeaf` in `apply-values.ts`); `compactAnswers(answers, fields)` (it now needs the questions) turns a Number's text into a JSON number, `0` stays an answer, and everything else passes through, so `parseAnswers` sees exactly what the API will. The native number and date inputs report `''` for text they can't parse (so `2026-02-30` can't be typed into the picker; the shared Temporal check still guards pasted or server-side values). `limitHint(field)` (`limit-hint.ts`) is the hint line under the label ("Between 0 and 50, whole numbers only.", "On or before December 31, 2026."), and `min`/`max` on the date input limit the picker. In Entry cards `onKeyDown` also cancels Enter in number, date and URL inputs. URL boxes are `type="url"` with a `https://` placeholder; the scheme rule (`http:`/`https:` only) comes from the shared check, not the browser (it accepts `javascript:`).
  - **Image compression (ticket 08).** In `UploadControl.send`, a picked JPEG, PNG or WebP of 512 KiB or more is shrunk first (`compressImageForUpload`, `lib/compress-image.ts`, on `browser-image-compression` 2.0.2, pinned): longest side 2560 px, quality 0.8 (PNG: 1), same type and name, EXIF orientation applied and metadata dropped. The decisions are pure and tested in `@repo/shared` (`image-upload.ts`): `shouldCompressImage`, `mayBeAnimated` (an animated PNG or WebP is sent untouched: a canvas keeps one frame), `chooseImageUpload` (the compressed copy replaces the original only if the same type and at most 90% of its size). The question's `check` runs on the original (a wrong type is refused at once; a size problem alone doesn't stop an image) and again on the file actually sent, so a 12 MB photo can pass a 10 MB limit; `createUpload` is given the sent file's name, type and size. The control shows "Reducing the image size…" and then "Reduced from X."; "Try again" resends the same file without compressing again. `useWebWorker: false` on purpose: the library's worker loads itself from cdn.jsdelivr.net at run time. The library's PNG path (UPNG) reduces the picture to `4096 * quality` colours, which is lossy.
- **Candidate sheet files (`components/dashboard/candidates/`):** `CandidateDetail` loads `getApplication` and `getApplicationFiles` together (the files DAL is `'use cache: private'` and holds metadata only; it throws on failure so nothing is cached, and the sheet then says "Couldn't load the files" rather than "No CV attached", using `unstable_rethrow` so a sign-in redirect isn't swallowed). A "CV" section sits between Contact and Answers, shown only when the form version the applicant saw asked for a CV (`cvMode` on the application detail isn't `off`) or a CV exists; a file question's answer (a file id) is looked up in the files and shown with the same `CandidateFile` row (name, type, size, length for media). Download goes through `DownloadFileButton` (client) calling the `getFileDownloadUrl` Server Action on each click, then following the returned link with a temporary `<a>`; the bucket's `Content-Disposition: attachment` saves the file and the page stays put. **Never mint a presigned link in a cached DAL function or render it into the page.**
  - **Repeating groups (ticket 05, ADR-0004).** `formatAnswer` (`format-answer.ts`) returns `FormattedAnswer`: text, a list of labels, `null` ("No answer"), or for a `repeating_group` a `GroupAnswer` (`{ entries: EntryRow[][] }`, a `{ label, answer }` row per answered sub-question, per Entry, in the applicant's order). Labels and option labels come from the `fields` of the form version stored with the application (the group's own `config.fields`), never the job's current form; blank sub-answers and empty Entries are left out, an unknown option id is "Unknown option", and a skipped group is `null` so it shows "No answer" like any unanswered question. `CandidateAnswer` (`candidate-answer.tsx`) renders any `FormattedAnswer`, and a group as an `<ol>` of bordered blocks, one `<dl>` per Entry; interviewers get the same blocks (only the move control differs).
  - **Number, date and URL answers (question-types ticket 04).** `formatAnswer` shows a number as `String(value)` (so `0` is an answer), a date with `Temporal.PlainDate.from(value).toLocaleString('en-US', { dateStyle: 'long' })` ("February 5, 2026"; MDN `Temporal/PlainDate/toLocaleString`; fixed locale and never `new Date(iso)`, which reads UTC midnight and shows the previous day west of UTC; the sheet is a Server Component and Node >= 26 has native Temporal), and a URL as a `LinkAnswer` (`{ href, text }`, tagged by `href` where a group is tagged by `entries`) only when `new URL()` gives `http:` or `https:`; any other value (such as `javascript:`) is plain text. `CandidateAnswer` renders a `LinkAnswer` with `target="_blank" rel="noopener noreferrer"`.
  - **Preview page (ticket 06).** `CandidateFile` (server) renders the name and details and hands them as children to `FileCard` (client), which shows Download always and, when `previewKindOf(mimeType)` (`@repo/shared`) has a kind, a **Preview `Link` with `target="_blank"`** to the file's own page (`filePreviewHref`, `file-preview-href.ts`): `app/(viewer)/dashboard/[companySlug]/jobs/[jobSlug]/candidates/[applicationId]/files/[fileId]/page.tsx`. Nothing is fetched by the sheet. The `(viewer)` route group has a bare layout (no sidebar, just `<Toaster />` for the Download button) and the page shows a slim header (file name, candidate, "Candidate" link back to `?application=<id>`, Download) over `FileViewer`, which fills the window (`VIEWER_HEIGHT` in `file-viewers.tsx`). The page loads `getApplication` then `getApplicationFiles` (a 404 or a file id not in that application is `notFound()`), and the viewer mints its link on mount via the `getFileViewUrl` action, so every visit gets a fresh link. To add a kind: extend `previewKindOf` and add a case to `FileViewer` plus a component in `file-viewers.tsx`. The page title is static (`File preview · Farraza`). **Video and audio** (`MediaViewer`): a native `<video controls>` / `<audio controls>` with `preload="metadata"` on the view link (the bucket serves range requests); the media elements have no `referrerpolicy`, so the default policy applies (origin only). A `error` event (a MOV with a codec the browser lacks) shows the same "Can't show this file" alert pointing at Download. The length shows in the row's details (`formatDuration` in `lib/format.ts`; the type name comes from `fileTypeLabel` in `@repo/shared`).
  - **PDF** (`PdfViewer`): an `<iframe src>` to the view link, the browser's own viewer, no `sandbox` (Chrome's PDF viewer won't run in a sandboxed frame; the bytes are on the bucket's origin with a pinned `application/pdf`). The Preview link is offered only when `usePdfPreviewSupported()`: `navigator.pdfViewerEnabled` and a fine pointer (checked in `FileCard`; the preview page doesn't check again, because the hook is false until hydrated and would flash a wrong message). Phones and tablets get only Download.
  - **Image** (`ImageViewer`, ticket 08): an `<img>` of the view link (`referrerPolicy="no-referrer"`, scaled to `max-h-[70vh]`, a skeleton until it loads, the Alert if it fails). Images used to open inline in the sheet; they now open on the preview page like every other kind (the link is minted by the same `getFileViewUrl` action). No CORS needed for an `<img>`.
  - **DOCX** (`DocxViewer`, `docx-render.ts`): `fetch` of the view link from the browser (needs bucket CORS `GET`), `docx-preview` loaded with `import()` on first use, rendered into **detached** elements, serialised to a string and shown as the `srcDoc` of an iframe with `sandbox=""` (no scripts, no same-origin: never add `allow-scripts` or `allow-same-origin`). Options that matter: `renderAltChunks: false` (an altChunk is a nested HTML page that would run with our origin if attached), `ignoreFonts: true`, `useBase64URL: true` (blob: URLs belong to our origin and don't load in an opaque-origin frame), `ignoreWidth`/`ignoreHeight` (reflow to the sheet). The output is stripped of links (`href` on `a`), event attributes and loading elements, `</style>` is escaped in style text, and the srcdoc starts with a CSP meta (`default-src 'none'; img-src data:; ...`). Files over `DOCX_PREVIEW_MAX_BYTES` (10 MB) are not rendered. A failure shows an Alert that points at Download.
